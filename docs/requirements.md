# 家賃入金チェック表 要件定義（v1.1）

作成日：2026-11-23（v1.1：契約100件、追加5機能、ダッシュボード、家賃改定の履歴を追加）

## 1. 目的と対象

- 小規模の個人大家（契約100件まで）が、家賃の入金確認、滞納の把握、契約・保険の期限管理、敷金の管理、空室・募集の管理、修繕・設備の履歴、固定資産税などの納付管理、家賃改定の試算、年間収支の集計を、1つのスプレッドシートで行えるようにする。
- Google スプレッドシートと Google Apps Script（GAS）で動かす。データは利用者自身の Google アカウント内にとどまり、開発者は預からない。
- 通知（メール・LINE）は今回の範囲に入れない。

## 2. 範囲

| 区分 | 内容 |
|---|---|
| 第1段階（手入力版） | 設定、台帳、入金記録、請求調整、入金チェック、保証会社入金、期限管理、敷金台帳、空室・募集、修繕履歴、税カレンダー、家賃改定試算、年間収支、ダッシュボード。判定は関数として実装し、テストする |
| 第2段階 | 銀行の入金通知メールの取り込み、明細CSVの取り込み、保証会社の合算入金の割り当て |
| 対象外 | 通知、請求書の自動発行、複数物件の別管理、決済、入居者向け画面、法令・税務の判断 |

## 3. シートと項目

### 3.1 設定
- 滞納の黄の開始（期日から何日超過で黄。初期値 1）
- 滞納の赤の開始（超過日数がこの値を超えたら赤。初期値 7）
- 更新期限の黄の開始（残り日数。初期値 90）、赤の開始（残り日数。初期値 30）
- 保証会社ごとの事故報告の期限（期日から何日以内。会社ごとに設定。初期値は空欄）
- 設備の次回の目安：黄の開始（残り日数。初期値 180）、赤の開始（初期値 60）
- 空室：黄の開始（空室日数。初期値 30）、赤の開始（初期値 60）、物件の総戸数
- 敷金の精算の目安日数（退去日から。初期値 30）
- 税の納付：黄の開始（残り日数。初期値 30）、赤の開始（初期値 7）、納付予定額を見る日数（初期値 90）
- 家賃改定の試算：想定退去率（初期値 5%）、退去時の空室想定日数（初期値 60）
- 基準日（空欄なら今日）
- 入金日の照合範囲（第2段階。期日の何日前から何日後まで。初期値 前10日・後20日）

### 3.2 台帳（1行＝1契約。100件まで）
号室、入居者名、登録名義（複数可。振込人名の照合用）、連絡先（電話・メール）、家賃、共益費、支払期日（毎月の日付、または月末）、契約開始日、契約更新日、保証会社名、保証の型（一般保証型／支払委託型／保証なし）、火災保険の期限、保証会社の契約期限、入居状況（入居中／退去済）、改定前の家賃、家賃の改定日（この日以降が現在の家賃）。号室は重複させない（入力規則で防ぐ）。

### 3.3 入金チェック（月別）
対象の年・月を選ぶと、台帳の入居中の全戸が並ぶ。項目：号室、入居者名、請求額（家賃＋共益費）、支払期日、入金額、最終入金日、状態、不足額、超過額、超過日数、滞納（黄・赤）、保証の型、事故報告の期限と残り日数。入金は別シート（入金記録）に1回ごとに入力し、入金チェックが対象月の分を集計する。分割で入金された場合も、1回ごとに1行を追加する。請求額をその月だけ変える場合は、請求調整シートに入力する。

### 3.4 期限管理
台帳の契約更新日、火災保険の期限、保証会社の契約期限について、契約ごとに残り日数と色（通常・黄・赤）を表示する。最も近い期限の残り日数も1列で出す。

### 3.5 敷金台帳
号室、入居者名、区分（敷金／保証金／その他預り金）、預かり額、預かり日、退去日、原状回復費、その他の控除、控除合計、返還額、追加請求額、状況（預り中／精算済）、精算の目安日、判定（預り中／精算期間内／精算遅れ／精算済）。預り中の合計額も出す。

### 3.6 空室・募集
号室、状況（空室／募集中／申込あり）、空室開始日、募集開始日、募集家賃、募集媒体、内見の件数、申込の件数、備考、空室日数、判定（黄・赤）、空室損失（概算）。空室数、空室率（総戸数に対する割合）、空室損失の合計も出す。

### 3.7 修繕履歴
実施日、号室（または共用）、区分（修繕／交換／点検／その他）、設備・箇所、内容、業者、費用、年間収支に含めるか、次回の目安（年）、次回の目安日、残り日数、判定。同じ号室・設備に、より新しい記録があれば「更新済」とする。

### 3.8 税カレンダー
年度、税目（固定資産税／都市計画税／その他）、対象、期、納期限、納付額、納付日、状況（納付済／未納）、残り日数、判定。今後の一定日数内の納付予定額と、納期限を過ぎた未納額も出す。

### 3.9 家賃改定試算
号室、入居者名、現行の家賃、周辺相場、相場との差、改定案の家賃、増減額、改定率、年間の増減額、期待される年間の影響額。想定退去率と空室想定日数は設定シートの値を使う。概算のモデルであり、結果を保証するものではない。

### 3.10 ダッシュボード
今月の入金の件数（入金済・黄・赤）と金額、期限が迫る契約の件数、空室数と空室損失、預り中の敷金と精算遅れの件数、今後の納付予定額、設備の目安超過の件数、年間の収入・経費・収支を、1画面にまとめる。

### 3.11 年間収支
月別の家賃収入（入金日ベース）、預り（参考）、修繕費（修繕履歴の「含める」のもの）、税金（税カレンダーの納付済のもの）、その他の経費（手入力）、経費合計、収支。年間合計も出す。

### 3.12 物件台帳・予定収支（v1.1）
- 物件ごとに、取得価格、取得日、土地の割合、固定資産税評価額（任意）、住宅用地の特例（小規模／一般／なし）、その他の年間経費、想定空室率を入力する。
- 台帳（契約）に「物件」列を持たせ、物件ごとに戸数、入居中戸数、月額家賃合計、固定資産税・都市計画税の推定、年間の予定収支、表面利回りを自動で出す。
- 予定収支シートで、対象年の月別に、見込み家賃、税の納付予定、設備交換の見込み、その他経費、収支を出す。
- 税の推定は目安であり、実際の納税通知書の額が正とする。税カレンダーの登録額と比べられるようにする。

## 4. 判定ルール

基準日は、シートを開いた日（今日）とする。請求額は台帳の家賃＋共益費とする。入金額は、その月の入金行の合計とする。

| ID | ルール |
|---|---|
| R-01 | 入金額が請求額と等しい場合、「入金済」とする |
| R-02 | 入金額が0より大きく請求額に満たない場合、「一部入金」とし、残額（請求額－入金額）を表示する |
| R-03 | 入金額が請求額を超える場合、「過入金」とし、超過額を表示する。翌月への充当は手入力で行う |
| R-04 | 入金額が0（または一部入金）で、基準日が支払期日以前の場合、「期日前」とする |
| R-05 | 入金額が請求額に満たず、基準日が支払期日を過ぎている場合、超過日数（基準日－支払期日）を求める。超過日数が黄の開始以上で赤の開始以下なら「黄」、赤の開始を超えたら「赤」とする |
| R-06 | R-05 の日数は、設定シートの値を使う |
| R-07 | 支払期日が、その月に存在しない日付（例：31日）の場合は、その月の末日とする |
| R-08 | 支払期日が土日祝であっても、期日の繰り下げは行わない。猶予が必要な場合は、設定で黄の開始日数を調整する |
| R-09 | 支払委託型の入居者の入金元は保証会社とする。保証会社からの1回の入金を複数の入居者に割り当てた場合、割り当ての合計が入金額と一致しなければ「差異」と表示する |
| R-10 | 一般保証型の入居者が赤になった場合、事故報告の期限（支払期日＋保証会社ごとの日数）までの残り日数を表示する。期限を過ぎていれば「報告期限超過」とする |
| R-11 | 期限管理は、残り日数が赤の開始以下（期限超過を含む）なら「赤」、黄の開始以下なら「黄」、それ以外は「通常」とする |
| R-12 | 年間収支の家賃収入は、入金日が属する月で集計する（入金日ベース）。請求額を超える過入金の分は、収入に含めず、備考に「預り」として出す |
| R-13 | 入金チェックは、対象月を選ぶと、台帳の「入居中」の契約から作られる。退去月は日割り計算をせず、請求調整シートで請求額を上書きできる |
| R-14 | 設備の次回の目安日は、実施日に目安の年数を足した日（月末の日は月末にそろえる）とする。残り日数が赤の開始以下なら「赤」、黄の開始以下なら「黄」、過ぎていれば「目安超過」とする。同じ号室・設備に、より新しい記録があれば「更新済」とし、判定しない |
| R-15 | 空室日数は、基準日－空室開始日（0以上）とする。空室日数が赤の開始以上なら「赤」、黄の開始以上なら「黄」とする。空室損失（概算）は、募集家賃×空室日数÷30を、円に四捨五入した額とする |
| R-16 | 敷金の返還額は、預かり額－（原状回復費＋その他の控除）とし、0未満にはしない。控除が預かり額を超えた分は、追加請求額とする。精算の目安日は、退去日＋精算の目安日数とし、状況が「預り中」のまま基準日が目安日を過ぎたら「精算遅れ」、退去日が空欄なら「預り中」、「精算済」はそのままとする |
| R-17 | 家賃改定の増減額は、改定案－現行、改定率は、増減額÷現行、年間の増減額は、増減額×12とする。相場との差は、（現行－相場）÷相場とする。値上げのときの期待される年間の影響額は、年間の増減額×（1－想定退去率）－想定退去率×現行家賃×空室想定日数÷30とする。値下げのときは、年間の増減額とする |
| R-18 | 税の納付は、納付日があれば「納付済」とする。未納の場合、残り日数（納期限－基準日）が負なら「納期限超過」、赤の開始以下なら「赤」、黄の開始以下なら「黄」とする。納付予定額は、未納で、納期限が基準日以降、基準日＋指定日数以内のものの合計とする |
| R-19 | 年間収支の経費は、修繕費（「含める」のもの、実施日の月）、税金（納付日の月）、その他の経費（手入力）の合計とする |
| R-20 | ダッシュボードの数値は、各シートの集計セルを参照し、別の計算を持たない |
| R-21 | ある月の請求額は、その月の請求調整があればそれを使う。なければ、家賃の改定日より前の月は改定前の家賃、それ以降は現在の家賃を使い、共益費を足す。複数回の改定は、請求調整で対応する |
| R-22 | 台帳の号室は重複させない。入金記録、請求調整、敷金台帳、家賃改定試算の号室は、台帳から選んで入力する |
| R-23 | 固定資産税・都市計画税の推定：評価額が未入力なら 取得価格×土地割合×土地評価割合、取得価格×(1−土地割合)×建物評価割合 で推定する。評価額の入力があればそれを使う。課税標準は 小規模住宅用地＝固定1/6・都市1/3、一般住宅用地＝固定1/3・都市2/3、特例なし＝そのまま。税率の初期値は固定1.4%・都市0.3%（設定で変更可） |
| R-24 | 物件の予定収支＝入居中の年間家賃×(1−想定空室率)−推定税額−その他の年間経費。表面利回り＝入居中の年間家賃÷取得価格（取得価格が空欄・0なら出さない） |
| R-25 | 税の採用額：物件ごとに、対象年の納期限で税カレンダーに登録（対象＝物件名）があれば、その合計を採用（入力値優先）。なければ推定額を採用する。予定年間収支（年間収支シート内）は、この採用額で、月別は登録分を納期限の月に、推定分を12等分で入れる |
| R-26 | 税制・法制で決まる値（固定資産税・都市計画税の税率、住宅用地の特例の割合、小規模住宅用地の面積上限）は、計算式に直接書かず、設定シートの「税制・法制の値」に置く。各値に確認日・出典のメモ欄を設ける |

### 4.1 税制・法制が変わったときの対応
1. 総務省・国税庁・自治体の発表や納税通知書で、変更の内容を確かめる。
2. 設定シートの⑩「税制・法制の値」を書き換える（税率は％、割合は「=1/6」の形）。
3. 同じ行の「確認日・出典（メモ）」に、書き換えた日と根拠を書く。
4. 物件台帳の税の推定と、年間収支の予定年間収支が変わったことを確かめる。
5. 新しい特例など、値で表せない変更は、物件台帳の評価額（使用値）〜税の合計（推定）の計算式と、`src/logic.js` の `estimatePropertyTax` を直し、テストを追加する。

## 5. 入金の取り込み（第2段階）

- 取り込み方法は、設定シートで「メール」「CSV」のどちらか、または両方を選べる。
- メール：銀行の入金通知メールを Gmail で受け取り、GAS が金額・入金日・振込依頼人名を読み取る。銀行ごとの形式は設定で登録する。最初は、利用者の家賃口座の銀行1行に対応する。
- CSV：銀行の明細CSVを、所定のシートに貼り付けて取り込む。最初は三井住友銀行の個人向け明細を想定し、列の並びは設定で変えられるようにする（下の 5.1）。
- 突合せ：登録名義（正規化したもの）と金額の両方が一致したら、自動で確定する。片方だけ一致したら「要確認」の候補とし、利用者が選んで確定する。どちらも一致しなければ「未照合」の一覧に入れる。
- 名義の正規化：全角・半角、カナ、空白、「カ)」などの略称を揃える。
- 重複の防止：入金日・金額・振込依頼人名の組が同じ入金は、二重に取り込まない。
- 銀行の通知や明細には、入居者のメールアドレスは含まれない。メールアドレスは突合せには使わない。

### 5.1 CSV取り込みの詳細（R-27〜R-30）

| ID | ルール |
|---|---|
| R-27 | 列の見つけ方：先頭20行の中から、日付・入金額・摘要の見出しがそろう行を見出しとする。見出しの名前は設定で追加できる（初期値：年月日／お預入れ／お取り扱い内容 など）。列の番号を設定したときは、名前より優先する。見つからなければエラーを表示する |
| R-28 | 読み取り：入金額が空・0・「-」の行（出金など）は対象外。日付は 2026/11/1、2026-11-01、2026年11月1日、R8.11.1、令和8年11月1日 などを読める。金額はカンマ・円・全角数字を読める。摘要の先頭の「振込」「ﾌﾘｺﾐ」などは取り除いて振込人名とする（取り除く文字は設定で変更可） |
| R-29 | 対象月：入金日が、どの月の支払期日の前10日〜後20日に入るかで決める。2つの月に入るときは期日が近い方、同じなら後の月。範囲の日数は設定で変更可 |
| R-30 | 照合：入居中の契約のうち、名義と金額（その月の請求額）の両方が一致する契約がちょうど1件なら自動確定。一方だけ一致する契約があれば要確認（名義だけ一致が1件ならそれを第一候補）。両方一致が2件以上のときも要確認。どれもなければ未照合。名義の正規化では、小さい「ャュョッ」なども大きい文字に揃える（銀行の表記に合わせる） |

## 6. 注意書き（設定シートの先頭と、README、販売時の説明文に載せる）

自動入金確認は、導入後の最初の数か月は、通帳や銀行の明細と必ず突き合わせて確認してください。銀行のメール形式の変更、振込人名の表記の違い、取消や組戻しなどで、結果が実際と異なることがあります。確認が終わるまでは、自動の判定を最終の記録として扱わないでください。年間収支は参考値です。確定申告の内容は、税務署や税理士に確認してください。

## 7. 非機能要件

- 利用者のGoogleアカウントだけで動く。外部のサーバーや有料のサービスを使わない。
- 個人情報（入居者名、連絡先）は、利用者のスプレッドシートにのみ保存する。公開するリポジトリには、架空のサンプルデータだけを入れる。
- 判定の関数は、シートから切り離して、Node.js で自動テストできるようにする。
- 第1段階（手入力版）は、GASを使わず、スプレッドシートの計算式だけで動く。計算式の結果は、判定の関数（`src/logic.js`）の結果と突き合わせて確認する（`tools/verify_template.py`）。GASは、第2段階の取り込みで使う。

## 8. 受け入れ基準

R-01〜R-26 のそれぞれについて、検証ケースを用意し、すべて通ること（検証ケースは `docs/test-plan.md`）。第1段階の完了条件は、判定の自動テストがすべて通ることと、利用者の Google アカウントでシートが動作することの両方とする。

## 9. 未決事項

- 保証会社ごとの事故報告の期限の初期値（保証会社ごとに契約で異なるため、利用者が入力する）
- メール取り込みで最初に対応する銀行
- 過入金の翌月充当を自動化するか（今回は手入力）
- 試用期間を30日にするか、入金2回分（約60日）にするか

| 公開版（Git・Public） | 手入力版（入金チェック、期限管理、物件台帳、敷金台帳、空室・募集、修繕履歴、税カレンダー、家賃改定試算、年間収支、ダッシュボード）、判定ロジック、テスト、要件定義、README、架空のサンプルデータ |
| 試用版（希望者に配布） | 自動入金確認（メール・CSV取り込み、保証会社の合算）を含む。配布時に期限日（配布日から約30日）をコードに埋め込み、期限後は取り込み機能だけが止まる。取り込める入居者は3戸まで |
| 製品版（購入者に配布） | 期限なし、戸数制限なし。買い切りで販売する。継続サポートは任意の追加メニューとする |

- 取り込み機能のコードは、非公開のリポジトリ（Private）で管理する。
- 試用版の再配布・転用の禁止は、利用規約に書く。返金には、販売の場の規定に沿って対応する。
- 技術的な制限は、正直な利用者向けの目安であり、コードを書き換える人を防ぐものではない。
